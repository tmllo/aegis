# Contract changelog

Any change to the shape of `storm_forecast.json` or `crew_data.json` goes here first, with date, who, what, and why. Tell the other person before merging.

- 2026-11-14 18:15: v1 created (starter kit).
- 2026-11-15: Crew scoring rule, for Emile's live check-in. The keys in `crew_data.json` are unchanged. A check-in is scored on the mean of that value and the previous 2 days, against the personal baseline (mean and sd of the first 14 days). Amber when the relevant side of z reaches 2. Red when it reaches 3, or when the raw value is outside `absolute_red`. Sleep, mood and exercise stay low-side only. Heart rate, blood pressure, glucose and temperature stay two-sided. Daily dose, cumulative dose and bone loss stay on their absolute limits and are not averaged. The full rule is the client-side section of `DATA_CONTRACT.md`. The simulated storm dose in the crew series moves from 10 Nov 2026 to 5 Sep 2026. That is a data change, not a schema change.
- 2026-11-15: New file `web/public/data/real_crew.json`. Inspiration4 CBC and chemistry (NASA OSDR OSD-575, crew C001–C004), scored against each person's pre-flight mean. Does not change `storm_forecast.json` or `crew_data.json`, and it is not an input to the check-in scorer. `far_from_baseline` means a post-flight value inside the printed lab range and at least 2 pre-flight sample SD from that person's mean. R+45 glucose under 50 mg/dL and R+45 potassium over 5.5 mmol/L are sample-handling artefacts. The C003 L-92 CBC row is excluded (shifted columns). Shape is the `real_crew.json` section of `DATA_CONTRACT.md`.
- 2026-11-15 (PROPOSED, not merged, Tomas): backend extras. `storm_forecast.json` events may carry `split: "live"` (flares scored by the server after the test period; never in `meta.metrics_test`), and a new `space_weather_now.json` (GOES protons, X-ray flares, Kp, NOAA scales, with `fetched_at` and `cached`). Details and reasons in `docs/backend/BACKEND-PLAN.md` section 4. Nothing changes until Emile agrees.
- 2026-11-15 (PROPOSED, Emile's app, no change to the three contract files): the Cabin screen reads `GET /api/health` (any JSON = server present) and then `GET /api/observations?subject=iss&kind=cabin`, expecting an array of `{ metric, t, value, quality }` with metric keys `cabin.pressure`, `cabin.ppo2`, `cabin.ppco2`, `cabin.temp`, `cabin.water_clean`, `cabin.water_waste`, `cabin.urine_tank` (and later `cabin.co`, `cabin.humidity`), units as observed (mmHg, deg C, percent). With no server it reads the recorded ISS Live snapshot in `web/public/samples/`. Limits live in `web/public/samples/cabin_catalog.json` (NASA: ppCO2, ppO2; Team: pressure, temperature, tanks). The only reader is `web/src/data/cabin.ts`.
- 2026-11-15 (PROPOSED, Tomas, mind lane; no change to the three contract files): Mind layer API for a 03 Mind screen. New metric keys `self.stress`, `self.energy`, `self.social`, `self.sleep_quality` (kind `self_report`, 1–5, five words per scale, hazard isolation); `self.mood` unchanged. New endpoints: `GET /api/checkin`, `POST /api/observations` (one check-in score, `{subject, metric, t, value}`), `GET/POST /api/tasks`, `POST /api/tasks/{id}/events`, `GET /api/progress`, `GET/POST /api/notes` (journal, needs header `X-Crew-Member` equal to the subject; text never in any other response or file), `GET /api/wellbeing` (weekly summary, counts only, no journal text). `GET /api/observations` keeps exactly `[{metric, t, value, quality}]` and now also returns check-in rows for a crew subject. Shapes and examples: `docs/backend/MIND-API.md`. Nothing changes in the app until Emile agrees.
- 2026-11-15 (PROPOSED, Tomas, live lane; no change to the three contract files or to any response shape): the server keeps data fresh while it runs. Each adapter with a timed catalog cadence (`5 min`, `daily`, `stream` = every 60 s) is re-run in the background, and the derived rows and `/data/*.json` are rebuilt, so `GET /api/observations` and `/data/*.json` can change between two calls. The store is a file by default (`server/data/aegis.db`), so check-ins, notes and tasks survive a restart. New: `GET /api/refresh` (schedule, last run, last error, `running`) and `POST /api/refresh` (run now, `?source=isslive` for one). Check-ins stay on the Mind lane's `POST /api/observations`. Examples: `docs/backend/LIVE-API.md`.
- 2026-11-15 (PROPOSED, Tomas, mind lane; no change to the three contract files): `GET /api/activities` (self-help activities from `server/catalog/activities.yaml`, suggested by open alerts) and `POST /api/activities/{id}/events`. System tasks gain `attrs.activities`. Verify rule tightened: a self-report alert task closes only when a newer reading is no longer flagged. Energy and sleep-quality scale words now equal `web/src/data/mind.ts` `SCALES`. Examples: `docs/backend/MIND-API.md`.
- 2026-11-15 (PROPOSED, Tomas, orbit lane; no change to `storm_forecast.json` or `crew_data.json`): globe orbit layer. New endpoints `GET /api/orbit` (station track with `sunlit` and `in_saa`), `GET /api/orbit/elements` (one station, one NORAD id, or a whole group; gzip when the client accepts it, `Content-Type` stays `application/json`), `GET /api/orbit/day`, `GET /api/orbit/groups`, and `GET /orbits/{iss,tiangong}.tle` (3-line TLE, the path the globe already fetches). Offline file `server/out/orbits/stations.json` (copy to `web/public/samples/orbits/stations.json`). Examples: `docs/backend/ORBIT-API.md`. Nothing changes in the app until Emile agrees.
- 2026-11-15 (PROPOSED, Tomas, EVA lane; no change to `storm_forecast.json` or `crew_data.json`): simulated suit API. `GET /api/eva/sites` (Moon 0.166 g, Mars 0.38 g, habitat dose in µSv/h, three waypoints), `GET /api/eva/sim` (walk, traverse, sample, emergency, optional storm), `POST /api/eva/assess` (the same alert rules on one snapshot). Everything is `quality: "simulated"`. Offline copies: `server/out/eva/moon_traverse_storm.json` and `mars_traverse_storm.json`. Examples: `docs/backend/EVA-API.md`. Nothing changes in the app until Emile agrees.
